# Граббер: плата + Raspberry Pi 4 → ноутбук (USB-вебкамера и веб-страница), без сжатия

Pi 4 подключается к ноутбуку одним кабелем USB-C, и ноутбук видит обычную **USB-камеру** «UVC Camera».
Одновременно то же видео (все поля, бит в бит) показывается в браузере на странице **http://169.254.10.1/** — по
кабелю LAN или Wi-Fi, см. [«Веб-страница»](#веб-страница-видео-в-браузере-кабель-lan-или-wi-fi).
Драйверы не нужны: Windows, Linux и macOS работают с ней как с любой вебкамерой (OBS, VLC, ffmpeg, «Камера»).

```
камера ─коакс─► J5 ─► буфер THS7314 ─► ADV7280-M ─шлейф CSI─► Pi 4 ─USB-C─► ноутбук
                     (5 В с GPIO Pi)    10-бит АЦП             склейка полей   720×576 NV12, 25 к/с
```

Проверено на железе 2026-11-21: Pi 4 2 ГБ, Raspberry Pi OS Lite (trixie, ядро 6.18), Windows-ноутбук — ровно 25,0 к/с,
камера видна как «UVC Camera». Пометка **[проверить]** — шаг написан по документации, но отдельно не запускался.

## Почему «без сжатия» и что такое NV12

* Декодер отдаёт полукадры (поля) 720×288, 50 штук в секунду. Программа `sprutm-uvc` на Pi складывает два
  соседних поля в кадр 720×576 строка через строку — так же, как они были в аналоговом сигнале. Ничего не
  масштабируется и не сжимается.
* Формат **NV12** (4:2:0): **яркость (Y) — каждый отсчёт АЦП как есть, бит в бит.** Цвет (U, V) по вертикали
  усредняется по двум соседним строкам **одного и того же поля** (так делают для чересстрочного 4:2:0 в MPEG-2), строки
  цвета двух полей чередуются. В PAL цвет соседних строк и так усредняется ещё при кодировании сигнала (линия задержки),
  поэтому глазом разницы с исходником нет.
* Встроенный деинтерлейсер чипа (I2P) **не используется**: он «додумывает» строки. Убирать гребёнку чересстрочности
  лучше на ноутбуке (OBS «Yadif 2x»), там это делается качественнее и обратимо — запись остаётся исходной.
* **Почему не YUY2 (4:2:2, совсем без изменений).** Ему нужно 720 × 576 × 2 × 25 = **20,7 МБ/с**. USB-C у Pi 4 —
  USB 2.0, а его контроллер (dwc2) в режиме устройства держит не больше **2048 байт за микрокадр = 16,4 МБ/с**: буферы
  FIFO аппаратно не больше 512 слов (проверено: 768 ядро отвергает, `Invalid parameter g_tx_fifo_size`, а при 3072
  байтах на пакет — `No suitable fifo found`). NV12 — **15,6 МБ/с**, влезает (~95 % канала): подключайте **напрямую в
  порт ноутбука**, без хабов и док-станций. Режим YUY2 в программе оставлен (`FORMAT=yuyv`), но на Pi 4 по USB он не
  пройдёт; для записи бит в бит нужен другой канал (Ethernet).

## Что понадобится

* Raspberry Pi 4 (2 ГБ хватает), карта microSD 8 ГБ+.
* Плата SPRUT-M, прошедшая шаги 1–7 из [bring-up.md](bring-up.md) (прозвонка, буфер, тестовая таблица).
* Шлейф камеры Pi **15–15 pin, шаг 1,0 мм**.
* Кабель **USB-C ↔ порт ноутбука с передачей данных** (кабели «только для зарядки» не подойдут).
  Лучше в порт USB-C ноутбука: он даёт Pi достаточно тока. Порт USB-A 3.0 (0,9 А) — на грани.
* Два провода от GPIO Pi к J4 (питание буфера, см. ниже).

## Подключение

1. **Шлейф CSI**: плата J1 ↔ разъём CAMERA Pi 4 (как в шаге 5 bring-up.md).
2. **Питание буфера 5 В от Pi** (отдельный блок не нужен, буфер берёт ~20 мА):

   | Контакт GPIO Pi | Куда на плате |
   |---|---|
   | pin 2 (5 В) | **J4, квадратная площадка 1** («+5V») |
   | pin 6 (GND) | **J4, площадка 2** |

   Pi сам питается от ноутбука по USB-C, 5 В на pin 2 — это та же шина.
3. **Видео** от камеры — на J5 (жила → квадратная площадка 1, оплётка → 2). J6/J7 (ТВ, монитор) можно не трогать.
4. Пока **не** подключайте Pi к ноутбуку — сначала установка.

## Установка на Pi (один раз)

1. Запишите карту в **Raspberry Pi Imager**: Raspberry Pi OS **Lite (64-bit)**. В настройках Imager включите SSH,
   задайте пользователя/пароль и Wi-Fi — Pi будет доступен по сети для установки и диагностики.
2. Загрузите Pi от обычного блока питания, зайдите по SSH и выполните:

   ```
   sudo apt update && sudo apt install -y git
   git clone -b rev-c-sprut https://github.com/inestvan/adv.git
   sudo sh adv/grabber/install.sh pal          # для камеры NTSC: ... install.sh ntsc
   sudo reboot
   ```

   Скрипт ставит компилятор, собирает `sprutm-uvc`, добавляет в `/boot/firmware/config.txt` блок
   (старая версия сохраняется в `config.txt.sprutm-bak`):

   ```
   camera_auto_detect=0
   dtoverlay=adv728x-m,adv7280m=1,media-controller
   dtoverlay=dwc2,dr_mode=peripheral
   ```

   и включает две службы: `sprutm-gadget` (создаёт USB-камеру) и `sprutm-uvc` (захват и склейка).

3. Выключите Pi, отключите блок питания и **подключите Pi кабелем USB-C к ноутбуку** — теперь он питается от него.

## Проверка на Pi (по SSH через Wi-Fi)

Для диагностики включите подробный журнал: в `/etc/default/sprutm-grabber` строка `EXTRA_ARGS=-v`, затем
`sudo systemctl restart sprutm-uvc`, и смотрите:

```
journalctl -u sprutm-uvc -f
```

Норма (по порядку):

```
decoder /dev/v4l-subdev0: 720x288 fields, PAL
running: /dev/video0 -> /dev/video1, fields 720x288 (bpl 1440), frames 720x576 NV12, parity over I2C
field parity locked (phase 0)                       <- через долю секунды (фаза 0 или 1 — обе нормальны)
host committed 720x576                              <- когда ноутбук открыл камеру
host started streaming 720x576 NV12 @ 25
fields 250, frames 125, dropped 0, no free buffer 0, phase 0     <- каждые 5 с
```

За 5 с `fields` растёт на 250, `frames` — на 125, `dropped` и `no free buffer` остаются около нуля.
Если в журнале `warning: input looks like NTSC` — камера NTSC, переустановите с `ntsc` (см. «Настройки»).
Питание: `vcgencmd get_throttled` → `throttled=0x0` (иначе Pi не хватает тока от порта ноутбука).

## На ноутбуке

**OBS Studio** (рекомендую, Windows/Linux/macOS):

1. Источники → **+** → «Устройство захвата видео» → устройство **UVC Camera**.
2. Разрешение/FPS: «Пользовательское», **720×576**, FPS **25**, формат видео **NV12**.
3. Правый клик по источнику → **Устранение чересстрочности → Yadif 2x**, порядок полей — **верхнее поле первым**
   (PAL). Получаются плавные 50 к/с.
4. Пропорции: аналоговое видео 4:3, а 720×576 — это «узкие» пиксели. Правый клик → Преобразовать →
   Изменить преобразование → размер **768×576** (или растянуть до 4:3).

**VLC**: Медиа → Открыть устройство захвата → DirectShow (Windows) → видеоустройство SPRUT-M. В «Расширенных
настройках» соотношение сторон 4:3. Видео → Устранение чересстрочности → Вкл, режим Yadif (2x).

**Запись без дополнительных потерь** (Windows, ffmpeg): кодек FFV1 сжимает без потерь в ~2–3 раза. [проверить]

```
ffmpeg -f dshow -video_size 720x576 -pixel_format nv12 -i video="UVC Camera" -c:v ffv1 -aspect 4:3 rec.mkv
```

В Windows камера называется **«UVC Camera»** (имя интерфейса UVC по умолчанию), в OBS ищите её под этим именем.

Linux-ноутбук: `ffplay -f v4l2 -input_format nv12 -video_size 720x576 -vf yadif=1 -aspect 4:3 /dev/videoN`.

## Веб-страница: видео в браузере (кабель LAN или Wi-Fi)

Та же программа одновременно с USB-камерой показывает видео в браузере. Нужен любой свежий Chrome, Edge или
Firefox, ничего ставить не надо.

* **Кабелем LAN (рекомендую): http://169.254.10.1/** Обычный сетевой кабель из Pi прямо в ноутбук. На прямом
  кабеле раздавать адреса некому: Windows примерно через 30–60 с сама берёт адрес 169.254.x.x, а у Pi на кабеле
  всегда есть постоянный адрес 169.254.10.1 (его ставит `install.sh`). Гигабит тянет **все 50 полей в секунду бит
  в бит** (20,7 МБ/с, как YUY2 — то, что не пролезает через USB-C); проверено: 50,0 полей/с, пропусков нет, Pi
  загружен на ~10 %. Wi-Fi ноутбука при этом можно не выключать.
  Имя `adv.local` по кабелю **не** подходит: оно выдаёт и адреса Wi-Fi, и браузер может пойти через Wi-Fi.
  Если Pi и ноутбук воткнуты в один роутер — открывайте `http://adv.local/`.
* **По Wi-Fi — http://adv.local/** (`adv` — имя Pi). Страница работает, но показывает столько полей, сколько
  пропускает сеть (у Pi 4 на 2,4 ГГц — около 2–3 в секунду): годится, чтобы проверить картинку и настройки, не для
  просмотра. Не держите открытыми лишние вкладки страницы: каждая забирает свою долю сети.

Что на странице:

* **Деинтерлейс** в браузере:
  * *Авто 50* (по умолчанию) — как в телевизоре: где картинка стоит, оба поля склеены (все 576 строк, мелкие детали
    и зерно не прыгают), где движение — недостающие строки интерполируются (нет гребёнки). 50 к/с. На неподвижной
    сцене дрожание между кадрами в 3–4 раза меньше, чем у Bob;
  * *Bob 50* — каждое поле отдельным кадром, строки всегда интерполируются: плавно, но мелкие детали прыгают на
    полстроки 50 раз в секунду;
  * *Weave 25* — два поля склеены как есть (гребёнка на движении); *Поле ×2* — строки поля просто удвоены.
* **Шумодав** — как 3D-шумодав телевизора: где картинка стоит, каждое новое поле подмешивается к накопленному
  (рекурсивно, в среднем ~7 кадров, для цвета ~9); где картинка изменилась — берётся новое поле, так что движение не
  размазывается; при смене сцены или пропуске поля накопление начинается заново. Мельтешение зерна от кадра к кадру
  на неподвижной сцене — примерно в 2–3 раза меньше (вместе с резкостью 64 и «Контурами» — до 10 раз).
* **Контуры** (*выкл / мягко / как ТВ*) — подчёркивание контуров на странице, после шумодава: та же форма, что у
  резкости декодера 245 (+6 дБ на 3,4 МГц), но мелкая рябь (шум) не усиливается. Резкость в самом декодере при этом
  должна быть 64 (выкл.): с 3D-гребёнкой резкость декодера усиливает и сетку поднесущей, на насыщенных цветах она
  упирается в пределы 1/254 и даёт ползущие полосы (так было на красном предмете).
* **Сглаживание** — убирает «лесенку» на почти горизонтальных краях (как скалер телевизора). Кадр в 576 строк
  рисует слегка наклонный край ступеньками по строке; здесь направление края находится по окрестности 9×5 точек и
  картинка сглаживается только вдоль края, поперёк не размывается. «Лесенка» на прорезях двери — на ~58 % меньше,
  мелкий текст не меняется.
* **3D-гребёнка** — как в хороших телевизорах. Обычно декодер отделяет цвет от яркости строчной гребёнкой, и она
  размывает тонкие штрихи (мелкий текст). Со включённой 3D-гребёнкой декодер отдаёт яркость без неё — со всей
  детализацией и с сеткой цветовой поднесущей 4,43 МГц, — а страница убирает сетку: складывает поле с тем же полем
  двумя кадрами раньше, где поднесущая PAL перевёрнута (проверено по записи: через 4 поля корреляция сетки
  отрицательная). Где есть движение — сглаживание по 3 точкам. Мелкий текст на ~40 % резче. Пока включена,
  **USB-вебкамера показывает сетку** (ей 3D-гребёнка не достаётся). Ключ `--comb3d` включает её при запуске.
* **Края: обрезать** (по умолчанию) — убирает края гашения, как overscan телевизора: по 9 точек слева и справа
  (остаётся стандартная активная ширина PAL 702) и по 4 строки сверху и снизу. Последняя строка нижнего поля —
  тёмная полустрока PAL, без обрезки она мигает внизу кадра.
* **Растяжение: чёткое** (по умолчанию) — кадр 702×568 растягивается до настоящих пикселей экрана фильтром Ланцоша,
  как это делает скалер телевизора: края резкие, без «мыла» и лесенки (перепады яркости на экране на ~20 % круче, чем
  при обычном сглаживании браузера; *мягкое* — как раньше). Видеокарте это почти ничего не стоит (< 1 мс на кадр).
* **Показ**: цвет; только яркость; *Клиппинг* — синим то, что ниже уровня чёрного (Y ≤ 16), красным — выше белого
  (Y ≥ 235). Удобно проверять пересвет.
* **Как ТВ** — показ, подобранный по фото AV-монитора рядом с ноутбуком: тени глубже (гамма 1,1) и цвета холоднее
  (синее, меньше красного). Ползунок **Холод** рядом: 100 % — как намерено, 0 — без сдвига цвета, до 200 %.
  Меняет только показ (и PNG); RAW кадр без изменений. Резкость как у монитора — «Контуры: как ТВ».
* **Гистограмма яркости** с минимумом, медианой, 1 % / 99 % и долей пересвеченного; линии на 16 и 235 — нормальные
  уровни чёрного и белого.
* **Состояние декодера** (регистры Status 1/2/3): есть ли сигнал, захват, стандарт, цветовая поднесущая, работает ли
  АРУ по пиковому белому; сколько полей доходит до браузера.
* **Настройки декодера**: яркость, контраст, насыщенность, оттенок, тестовая картинка, **резкость** (подчёркивание
  контуров, регистр 0xFB: 64 — выключено, как у чипа по умолчанию; больше — резче). Действуют сразу, но **не
  сохраняются** — после перезапуска Pi возвращаются заводские. Двойной щелчок по ползунку — значение по умолчанию.
* **PNG** — снимок картинки до растяжения (702×568, с выбранным показом); **RAW кадр** — два последних поля, склеенные без всякой обработки, файл
  `.yuv` (UYVY 720×576; открыть: `ffplay -f rawvideo -pixel_format uyvy422 -video_size 720x576 файл.yuv`).
* **⛶** или клавиша **F** — во весь экран.
* Выбранные режимы показа (деинтерлейс, показ, «Холод», шумодав, края, растяжение, пропорции) браузер запоминает
  и восстанавливает при следующем открытии страницы. 3D-гребёнка и резкость хранятся в декодере: при запуске их
  задают ключи `--comb3d` и `--peaking N` в `EXTRA_ARGS`.

Как это устроено: `grabber/web.h` — маленький HTTP + WebSocket сервер внутри `sprutm-uvc`, без библиотек. Каждое поле
декодера уходит в браузер как есть (заголовок 16 байт + 720×288 UYVY), браузер рисует его через WebGL (BT.601,
студийный диапазон). Если браузер не успевает принять поле, следующее для него пропускается — задержка не копится.
Порт задаётся `WEB_PORT=` в `/etc/default/sprutm-grabber` (`0` — выключить страницу).

## Вывод на HDMI Pi: минимальная задержка

Монитор или телевизор подключается прямо к Pi кабелем **micro-HDMI → HDMI** (лучше в порт HDMI0, ближний к USB-C).
Ноутбук для этого не нужен; USB-камера и веб-страница работают параллельно. Включается ключом `--hdmi` в
`EXTRA_ARGS` (`/etc/default/sprutm-grabber`), потом `sudo systemctl restart sprutm-uvc`. Монитор можно подключать и
отключать на ходу: программа проверяет разъём раз в 2 с.

* **Режим монитора** — 50 Гц, если монитор его умеет (его родное разрешение @50, иначе 1920×1080@50, 1280×720@50,
  720×576@50): одно обновление экрана на одно поле, движение без рывков. Монитор без 50 Гц — его основной режим
  (обычно 60 Гц), в журнале предупреждение: движение чуть дёргается. Задать вручную: `--hdmi-mode 1280x720@50`.
* **Картинка** — та же обработка, что на странице по умолчанию: 3D-гребёнка (если включена, `--comb3d`), деинтерлейс
  «Авто 50», шумодав, обрезка краёв гашения; кадр 4:3 вписан в экран с чёрными полями. Растягивает до разрешения
  монитора аппаратный масштабатор Pi (HVS), он же переводит цвета BT.601 в RGB. «Как ТВ», «Холод» и Ланцош —
  только на странице.
* **Как устроено** (`grabber/hdmi.h`): без рабочего стола и без видеокарты. Поле обрабатывается процессором в трёх
  потоках (~5 мс на поле, вместе с захватом ~0,9 ядра из 4), кадр в формате NV16 (4:2:2) отдаётся плоскости вывода
  DRM, показ — со следующим обновлением экрана.
* **Задержка** (измерено на Pi на принудительно включённом выходе 1280×720@50): от готового поля до начала его показа
  на экране — **10–22 мс, в среднем ~16 мс** (обработка ~5 мс + ожидание ближайшего обновления 0–20 мс: часы камеры
  и монитора независимы, фаза случайна при каждом включении и потом почти не уплывает). Для сравнения, страница в
  браузере: ~25–40 мс до экрана ноутбука. Плюс у любого вывода: само поле приходит в Pi целиком (верх поля ждёт
  низ, до 20 мс), развёртка экрана сверху вниз (до 20 мс) и собственная задержка монитора (у компьютерных
  мониторов ~5–15 мс, у телевизоров бывает больше — включите на нём «игровой режим»).
* Если кадр опоздал к обновлению, следующий за ним не ждёт в очереди, а сразу заменяет его (иначе вся картинка
  отставала бы на лишний кадр навсегда): в журнале с `-v` это счётчик `late`, обычно 0–5 за 10 с.

С `-v` раз в 10 с в журнале строка `hdmi: … frames/s shown, field -> refresh … ms` — задержка и скорость вывода.

## Настройки (`/etc/default/sprutm-grabber`)

```
STD=pal          # pal: 720x576 @ 25; ntsc: 720x480 @ 29.97 (после смены — sudo reboot)
FORMAT=nv12      # nv12 (по умолчанию) или yuyv — на Pi 4 по USB не пролезает, см. выше
WEB_PORT=80      # веб-страница: http://169.254.10.1/ по кабелю, http://adv.local/ по Wi-Fi; 0 — выключить
EXTRA_ARGS=      # дополнительные ключи sprutm-uvc, см. ниже
```

| Ключ | Когда нужен |
|---|---|
| `--swap` | На **неподвижной** картинке видны «ступеньки»/двоение каждой строки: верхнее и нижнее поле перепутаны местами |
| `--invert-phase` | Неподвижная картинка чистая, но **движение дёргается вперёд-назад**: поля склеиваются из соседних кадров. Ключ переворачивает пары, результат сохраняется между запусками |
| `--phase 0` или `--phase 1` | Только если I²C не работает: чётность задаётся вручную, без чтения из чипа. Нужное значение может меняться при каждом запуске, поэтому это аварийный режим |
| `--peaking N` | Резкость декодера при каждом запуске (0…255, 64 — выключено). С 3D-гребёнкой ставьте 64, а резкость давайте «Контурами» на странице. Без 3D-гребёнки резкость декодера можно подобрать ползунком и записать сюда: `EXTRA_ARGS=--peaking 160` |
| `--comb3d` | Включить 3D-гребёнку страницы при запуске (строчная гребёнка яркости декодера выключена). На USB-камере будет мелкая сетка |
| `--hdmi` | Видео ещё и на HDMI-выход Pi (минимальная задержка), см. [«Вывод на HDMI Pi»](#вывод-на-hdmi-pi-минимальная-задержка) |
| `--hdmi-mode WxH@R` | Режим HDMI вручную, например `--hdmi-mode 1280x720@50` (по умолчанию — разрешение монитора @50 Гц) |
| `-v` | Статистика в журнале раз в 5 с; `-v -v` — ещё и все USB-запросы ноутбука |

Несколько ключей пишутся через пробел: `EXTRA_ARGS=--swap -v`. После правки: `sudo systemctl restart sprutm-uvc`.

## Как это устроено (для понимания)

* **USB-камера** — стандартный механизм Linux (configfs, функция `uvc`). Скрипт `sprutm-gadget.sh` описывает
  ноутбуку один формат: несжатый NV12 720×576 при 25 к/с, изохронная точка 2 × 1024 байт.
* Драйвер `f_uvc` растягивает каждый кадр ровно на свой интервал (40 мс = 320 микрокадров по ~1956 байт). Интервал
  программа обязана задать через `VIDIOC_S_PARM`, иначе ядро берёт 15 к/с по умолчанию и поток идёт на 15 к/с.
* **sprutm-uvc** (`grabber/sprutm-uvc.c`): отвечает на запросы ноутбука (probe/commit), принимает поля от приёмника
  камеры Pi (unicam), склеивает пары и отдаёт кадры в USB.
* **Чётность поля.** Приёмник камеры Pi не сообщает, верхнее поле пришло или нижнее, а склеить их нужно строго в
  правильном порядке. Поэтому программа раз в секунду читает у ADV7280 по I²C бит `EVEN_FIELD` (регистр 0x45
  подкарты прерываний, UG-637) в середине поля и привязывает его к счётчику кадров приёмника. Счётчик растёт на
  каждом поле, даже потерянном, поэтому привязка не сбивается. Смена подкарты (регистр 0x0E) сразу возвращается
  назад; драйвер в это время к чипу не обращается.
* Склейка проверена тестом `grabber/test_weave.c` (раскладка строк, YUY2 байт-в-байт, NV12: яркость байт-в-байт и
  усреднение цвета внутри поля, чётность):
  `gcc -O2 -Wall -o test_weave grabber/test_weave.c && ./test_weave`.

## Если что-то не так

| Симптом | Где искать |
|---|---|
| Ноутбук не видит камеру | кабель с данными; `ls /sys/class/udc` (пусто — нет `dtoverlay=dwc2,dr_mode=peripheral`); `systemctl status sprutm-gadget` |
| Камера есть, картинки нет / таймаут | `journalctl -u sprutm-uvc`: `field parity not locked` — I²C (`ls /dev/i2c-10`), попробуйте `--phase 0`; `no unicam capture node` / `no adv7180 subdevice` — шаги 5–7 bring-up.md и строка `media-controller` в config.txt |
| `capture STREAMON: ... format mismatch` | формат декодера и приёмника не совпал: `media-ctl -p`, сравнить размеры; стандарт (PAL/NTSC) |
| `the decoder is in progressive (I2P) mode` | в config.txt нет `,media-controller` у `dtoverlay=adv728x-m` — исправить и перезагрузить |
| Ровно ~15 к/с вместо 25 | старая сборка без `VIDIOC_S_PARM`: переустановить (`install.sh`) |
| Растёт `no free buffer`, картинка рвётся | USB не успевает: подключить напрямую в порт ноутбука, без хаба; другой порт/кабель |
| Камера видна, кадры пустые/чёрные, в `dmesg` `No suitable fifo found` | в `/sys/kernel/config/usb_gadget/sprutm/functions/uvc.0/streaming_maxpacket` больше 2048 — переустановить |
| Pi перезагружается, `throttled` ≠ 0x0 | мало тока от порта: порт USB-C ноутбука или USB-хаб с внешним питанием |
| Чёрная картинка, `fields` растёт | нет сигнала на входе: 5 В на J4 (буфер), камера, стандарт (`input looks like ...` в журнале) |
| Ступеньки на неподвижном / дёргается движение | `--swap` / `--invert-phase` (таблица выше) |
| Страница не открывается | Pi включён и `systemctl status sprutm-uvc` активна; по прямому кабелю — адрес `http://169.254.10.1/` и подождать ~1 мин, пока Windows возьмёт адрес 169.254.x.x (`ipconfig`: у «Ethernet» адрес 169.254…); по Wi-Fi — открыть по IP (`hostname -I` на Pi); в журнале `web page off: port 80` — порт занят другой программой |
| На HDMI ничего нет | ключ `--hdmi` в `EXTRA_ARGS` и `sudo systemctl restart sprutm-uvc`; в журнале `hdmi: …x…@… on connector`; кабель в порт HDMI0; без рабочего стола (Raspberry Pi OS Lite) — с рабочим столом экраном владеет он |
| По кабелю тоже мало полей в секунду | открыт `adv.local` вместо `169.254.10.1` — браузер ушёл через Wi-Fi |
| Картинка белёсая, чёрное серое (на гистограмме нет ничего ниже ~100), «Захват (IN_LOCK)»: нет | выключен входной кламп декодера: драйвер ядра adv7180 затирает бит CCLEN (регистр 0x14, бит 4) при старте и при каждом переключении «Тестовой картинки». `sprutm-uvc` включает его сам и проверяет раз в секунду (в журнале один раз: `decoder input clamp was off ... turned on`). Если запускаете захват другой программой — `sudo i2cset -f -y 10 0x21 0x0e 0 && sudo i2cset -f -y 10 0x21 0x14 0x10` |
| На странице мало полей в секунду, «пропуск (сеть)» растёт | Wi-Fi не тянет 20 МБ/с: подключить кабель LAN |

## Вернуть Pi в обычный режим

```
sudo systemctl disable --now sprutm-uvc sprutm-gadget
sudo cp /boot/firmware/config.txt.sprutm-bak /boot/firmware/config.txt
sudo reboot
```

Одновременно с USB-камерой ustreamer на том же Pi не запустить: захват занимает приёмник камеры.
